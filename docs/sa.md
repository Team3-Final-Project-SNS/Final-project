## 1. 프로젝트 개요

### 1. 프로젝트명

- **한끼팟**

### 2. 핵심 목적

- **대학 내의 사람들을 식사라는 매개로 연결한다.**

### 3. 타겟 사용자

- 첫 진입 대학 관계자
- 학식, 점심, 저녁 메이트를 찾는 대학생
- 초기 핵심 타겟 시점
    - 신학기 (3월, 9월)
        - 새 인간관계 형성 니즈 최고조 → 신입생 집중 유입
    - 복학생
        - 학교 복귀 후 아는 사람 적음 → 자연스러운 유입 시나리오
    
    → 온보딩 문구 / 마케팅을 시점 별로 다르게 구성
    

### 4. 플랫폼

- **Web 기반** (반응형 디자인)

### 5. 차별 포인트

## 2. 핵심 사용 시나리오

```java
[A: 24학번, 1시 반에 수업 끝남]
   ↓
게시글 작성: "밥 먹을 사람? 1시 반에 수업 끝남"
+ 책임비 500P 설정 (등록자 500P 예치)
   ↓
[B: 22학번 선배가 신청]
   ↓
B가 게시글에 신청 → 동일 500P 예치 → 선착순 매칭 확정
   ↓
1:1 채팅방 자동 생성
   ↓
"수업 어디서 끝나? 어디서 만나자"
"뭐 먹을래요?"
"22학번인 내가 추천해줄게, 여기 가봤어?"
   ↓
오프라인 만남
   ↓
인증 1차/2차 (장소인증 / 만남인증 / 등록자 표시 → 신청자 스캔)
   ↓
만남 완료 → 예치 포인트 양쪽 반환
   ↓
식대 N빵 (오프라인 정산)
```

## 3. MVP 핵심 기능

### 1. 학교 이메일 가입

- **학교 이메일(.ac.kr) 기반 OTP 인증**
- 한 학교 이메일당 한 계정
- 가입 시 이름·닉네임·학과·학번·생년·성별 입력
- 가입 흐름
    1. 이메일 입력 → OTP 발송
    2. OTP 검증 + 회원 정보 입력
    3. 약관 동의 → 가입 완료

---

### 2. 게시글

### 1. 게시글 작성

- 입력 항목
    - 만남 희망 시간 (필수)
    - 만남 장소 선택(필수) - 정문, 후문, 기숙사, 동아리관 → 추후 장소 선택 기능으로 고도화
    - **모집 인원 설정 (필수, 최소 2명 ~ 최대 10명)** — 2명이면 1:1, 3명 이상이면 단체(1:N) 매칭으로 분기
    - 희망 식당 (선택)
    - 한마디 (수업 끝나는 시간 등 하고싶은 말)
    - **책임비 포인트 설정** (최소 200P, 100P 단위 증감, 본인 보유 한도 내 자유)
- 작성 즉시 책임비 포인트 예치 (잔액 차감, point_transaction에 DEPOSIT 기록)
- 잔액 부족 시 작성 불가

---

### 2. 게시글 목록 조회 / 필터링

- 같은 학교 게시글만 노출 (작성자의 university_id 기준)
- **책임비 포인트가 높은 게시글이 상위 노출 가능**
- **만남 시간 빠른(임박) 순으로 상위 노출 가능**
- **게시글 작성 최신 순으로 상위 노출 가능**

---

### 3. 게시글 수정 / 삭제

- 본인 게시글만 가능
- **`OPEN` 상태일 때만** 수정·삭제 가능 ( 매칭 전에만 수정 삭제 가능)
- 삭제 시 예치 포인트 반환

---

### 3. 신청 / 매칭 (1:1 / 단체 선착순)

- 신청자가 상세페이지에 들어가서 "신청하기" 클릭
- **등록자와 동일한 예치 포인트 차감**
- **선착순 매칭 - 고도화에서 동시성 적용 (Redis 분산락, DB 비관락 등)**
    - 1:1 매칭(정원 2명): 락 즉시 실패 전략 — 자리 없으면 바로 실패 응답 (빠른 UX)
    - 단체(1:N) 매칭(정원 3명 이상): 락 500ms 대기 전략 — 동시 신청 시 남은 자리 수만큼 순차적으로 채워서 빈자리 없이 정확히 마감
- 본인 게시글 신청 불가
- 게시글 정원(`maxApplicants`) 도달 시점에 게시글 상태가 `MATCHED`로 전환됨
- 게시글 매칭 인원(`currentApplicants`)이 정원(`maxApplicants`)에 도달하지 않더라도 만남 시간이 지날 경우 게시글 상태가 `MATCHED`로 전환됨

---

### 4. 채팅 (WebSocket / STOMP)

- 첫 신청자 매칭 확정 시 게시글 정원에 맞는 채팅방 자동 생성 (정원 2명 → 1:1 채팅방 / 정원 3명 이상 → 그룹 채팅방)
- 단체 매칭에서 이후 신청자는 기존 그룹 채팅방에 게스트로 순차 추가
- 실시간 채팅 대화로 메뉴·식당 등 세부 사항 확정
- 최종 만남 시간 +2h 후 채팅방 비활성화 (조회만 가능) → 일방적인 연락 방지
- 단체 매칭에서 신청자가 취소하면 해당 신청자만 채팅방에서 퇴장, 나머지 참여자 채팅방은 유지
- 단체 매칭에서 등록자가 취소하면 해당 매칭 자체 취소 - 파투

---

### 5. 오프라인 인증 (GPS 장소 인증 + QR 만남 인증)

- **1단계 — 장소 인증 (GPS)**
    - 만남 장소 기준 GPS 반경 50m 이내 진입 시 장소 인증
    - 활성화 시간: 약속 시간 10분 전 ~ 30분 후
    - 양측 모두 인증 완료 시 장소 인증 완료, QR 단계 진입
    - author_place_verified_at / applicant_place_verified_at 로 변경
    - 지도 UI: 약속 장소 반경 내 위치와 상대방 위치만 표시 (파란 점, 빨간 점)
- **2단계 — 만남 인증 (QR)**
    - 장소 인증 완료 시 서버가 만남 QR 토큰 발급 (TTL: 장소 인증 완료 시점 + 30분)
    - 등록자가 QR 표시 → 신청자가 스캔
    - QR 인증 완료 시 만남 완료 처리, 예치 포인트 반환
- 인증 시각 분리 저장(`author_place_verified_at`, `applicant_place_verified_at`) → **노쇼 판정 근거**
- 만남 완료 시 GPS 인증은 비활성화
- GPS 장소 인증 화면 (위치 공유 상세)
    
    **위치 데이터 설계 근거**
    
    - 위치 정보는 장소 인증 단계에서만 필요한 **임시 데이터**
    - 만남 완료/취소/노쇼 시 즉시 삭제 처리 (개인정보 최소 수집 원칙)
    - `meet_verifications` 테이블과 분리하여 별도 `user_location` 테이블로 관리
    
    **업데이트 주기 설계 근거**
    
    | 주기 | 장단점 |
    | --- | --- |
    | 1초 | 너무 잦음 → 서버 부하, 배터리 소모 |
    | 5초 | 균형점 ✅ (자전거/킥보드 이동 속도 고려) |
    | 10초 | 너무 느림 → 위치 부정확 |
    - 자전거(약 15km/h) 기준 5초에 약 20m 이동 → 50m 반경 내 감지 가능
    - 전동킥보드(약 25km/h) 기준 5초에 약 35m 이동 → 허용 범위 내
    
    **데이터 생명주기**
    
    ```java
    생성 → 매칭 확정 시 (MATCHED) 레코드 생성
    업데이트 → 장소 인증 단계에서 5초마다
    삭제 → COMPLETED / CANCELLED / NO_SHOW 시 자동 삭제
    ```

### 6. 포인트 시스템

| 이벤트 | 변동 |
| --- | --- |
| 가입 시 | +10,000P |
| 게시글 작성 시 | 설정한 책임비 포인트 예치 |
| 신청자 매칭 시 | 등록자와 동일 포인트 예치 |
| 만남 정상 완료 | 예치 포인트 전액 반환 |
| 약속시간 이전 취소 | 취소한 사용자의 예치 포인트 50%만 반환 |
| 노쇼 | 노쇼한 사용자 예치 포인트 차감 |

| 타입 | 부호 | 설명 |
| --- | --- | --- |
| `SIGNUP_BONUS` | + | 가입 보너스 (10,000P) |
| `DEPOSIT` | - | 게시글 작성·매칭 시 예치 |
| `REFUND` | + | 정상 완료 또는 사전 취소 반환 |
| `PARTIAL_REFUND` | + | 매칭 취소 시 50% 반환 |
| `FORFEITURE` | - | 노쇼 시 환수 |

### 정합성 보장

- 포인트는 `user.freePoint /user.paidPoint`로 나뉘며 **캐시 컬럼**이다. 실제 정합성은 `point_transaction` 누계로 검증한다.
- 무료 포인트(freePoint) : 가입 보너스, 신고 채택 보상, 후기 포상 등 - 환불 불가
- 유료 포인트(paidPoint) : 현금 결제로 충전된 포인트 - 환불 가능(결제 취소시)
- 모든 거래 직후 `balance_after`를 함께 기록하여 추적 가능하도록 한다.
- 동시 거래에 대비해 `user.point` 갱신은 비관락 또는 낙관락 사용 (Redis 분산락 보조 가능).

### 매칭 취소 시 포인트 반환 정책 (1:1 vs 단체)

- **1:1 매칭**: 취소한 사람은 예치 포인트 50% 몰수, 상대방은 100% 반환. 등록자가 취소하면 게시글은 `CANCELLED`로 전환
- **단체(1:N) 매칭 — 신청자 취소**: 취소한 신청자만 예치 포인트 50% 몰수, 채팅방에서 퇴장. 나머지 신청자와 모임은 그대로 유지, 게시글은 `OPEN` 유지 가능
- **단체(1:N) 매칭 — 등록자 취소**: 등록자 예치 포인트 50% 몰수, 모든 신청자 예치 포인트는 100% 반환. 전원 강제 퇴장, 게시글은 `CANCELLED`로 전환

### 잔액 부족 처리

- 게시글 작성·신청 시점에 잔액 검증
- 잔액 부족 시 `POINT_001` 에러 반환
- 자연 회복 또는 충전 시스템은 Phase 2 단계

### 7. 회원가입 시 약관 동의

- 우리 서비스의 목표는 순수하게 밥약을 잡는 용도입니다.
- **만남에서 발생한 식대는 만나서 N빵이 기본 원칙입니다.**
- 부적절한 게시물은 신고의 대상이 되며 관리자가 임의로 삭제 할 수 있습니다. → 신고 포상금 50P
- 용도 이외 사용 시 벌어지는 문제에 대해 당사는 법적 책임지지 않습니다.

<details>
<summary><strong>4. 부가 기능, 고도화</strong></summary>

## 4. 부가 기능, 고도화

> MVP 출시 후 사용자 데이터 보고 단계별 도입.
> 

### 부가 기능

#### 1. 마이페이지

- 내 프로필 조회 / 수정 (닉네임, 학과, 비밀번호)
- 보유 포인트 잔액 확인
- 내가 작성한 게시글 목록
- 매칭 이력 조회 (완료 / 노쇼 / 취소)
- 포인트 거래 내역 조회 (`point_transaction` 기반)

---

#### 2. 계정 관리

- 비밀번호 변경
- 로그아웃
- 계정 정지 및 탈퇴
    - 계정 정지 중 탈퇴 불가
        - 계정 정지 상태에서는 탈퇴 기능이 비활성화된다
        - 정지 기간이 만료되면 자동으로 정지가 해제된다
        - 정지 해제 이후 탈퇴 및 재가입이 가능하다
    - 영구정지
        - 영구 정지된 계정은 탈퇴도 불가능하다
        - 해당 학교 이메일로 신규 가입이 영구 차단된다
    - 정지 단계별 기간(횟수 → 신고 당한 횟수)
        - 1회: 경고
        - 2회: 경고
        - 3회: 3일 정지
        - 4회: 10일 정지
        - 5회: 30일 정지
        - 6회 이상: 영구 정지
- 학교 이메일 재인증(탈퇴 → 재 회원가입)

---

#### 3. 알림

- 알림 목록 조회
- 미확인 알림 카운트 표시 (헤더 벨 아이콘)
- 알림 읽음 처리
- 알림 종류
    - 매칭(4)
        - 게시글 신청(등록자에게)
        - 매칭 확정(신청자에게)
        - 매칭 취소(등록자 취소)
        - 매칭 취소(신청자 취소)
    - 만남 시간(4)
        - 만남 시간 알림 (30분 전)
        - 만남 시간 알림 (15분 전)
        - 만남 시간 임박 (5분 전)
        - 만남 시간 지남 (10분 후)
    - 만남 완료 / 후기(4)
        - 만남 완료(후기 작성 유도)
        - 후기 작성 마감 임박(7일째 아침 7시)
        - 후기 작성 포인트 지급(50P)
        - 매너 온도 변화(오른 경우에만 알림)
    - 채팅 / 장소 인증(3)
        - 채팅 메시지 수신
        - 장소 인증 완료
        → 1:1: 상대방에게만 발송
        → 그룹: 모임 참여자 전원에게 발송
        - 그룹 채팅방 신청자 퇴장(취소) → 등록자에게만 발송
    - 노쇼(2)
        - 노쇼 예정 상태 안내
        - 노쇼 확정 알림
    - 만남 시간 연장(4)
        - 시간 연장 요청(상대방에게)

### 백엔드 기능 별 MVP 최적화

#### 1. 동시성 제어

- **기술**: Redis 분산락, DB 비관락
- **적용 위치**: 선착순 매칭, 포인트 차감, 게시글 상태 변경
- **내용**
    - MVP: `post_id` UNIQUE 제약으로 1차 방어
    - 고도화: Redis 분산락(`lock:post:{postId}`)으로 동시 요청 직렬화
    - 트랜잭션 내 게시글 상태 변경 + 매칭 생성 + 포인트 차감 + 채팅방 생성 원자적 처리

---

#### 2. 성능 최적화 (부하 테스트 + 성능 병목 개선 + 캐싱)

- **기술**: Redis Cache, QueryDSL, Index 튜닝, K6
- **내용**
    - Redis ZSet으로 책임비 포인트 기반 게시글 상위 노출
    - QueryDSL 동적 쿼리 + 페이징 최적화
    - EXPLAIN 기반 실행 계획 분석 → 인덱스 추가
    - K6 부하 테스트 → Latency(P95/P99), Throughput(RPS), Error Rate 기록
    - 개선 전후 수치 비교 문서화

---

#### 3. 로그·모니터링

- **기술**: Logback / SLF4J, Prometheus + Grafana / n8n
- **적용 위치**: 전체 API, 포인트 거래, 노쇼 판정, GPS/QR 인증
- **내용**

    - 모니터링 지표 선정 및 수집 근거 문서화

### AI 기능 별 MVP

#### 1. LLM 구조화 출력 + 프롬프트 엔지니어링

- **적용 후보**: 노쇼 이의제기 사유 분석
- **내용**
    - LLM 응답을 DTO/JSON Schema로 파싱 → DB 저장
    - `max_tokens`, `temperature` 명시 설정 및 근거 문서화
    - 도메인별 프롬프트 템플릿 최소 2개 분기 (예: 신입생용 / 복학생용 온보딩 메시지)
    - 프롬프트 코드 하드코딩 X → 서버 재배포 없이 수정 가능한 구조
    - 프롬프트 개선 이력 최소 3회 기록

---

#### 2. Tool Calling 기반 AI-백엔드 API 연동

- **적용 후보**: AI 밥약 어시스턴트
- **시나리오 예시**
    
    ```
    사용자: "오늘 12시에 정문 근처에서 밥 먹을 사람 있어?"→ LLM이 searchPosts(time="12:00", place="정문") 호출→ LLM이 checkUserPoint(userId) 호출 → 포인트 충분한지 확인→ "현재 12시 정문 게시글 2개가 있어요. 포인트도 충분하니 바로 신청할 수 있어요!"[장애 상황] searchPosts API 타임아웃→ "지금 게시글 조회가 어려워요. 잠시 후 다시 시도해주세요."
    ```
    
- **Tool 후보**: `searchPosts` / `checkUserPoint` / `getMatchStatus`

---

#### 3. AI 기능 장애 격리 + 비용 인식 설계

- **내용**
    - LLM API 장애 시 핵심 기능(매칭, 포인트, 채팅)에 영향 없어야 함
    - Fallback 최소 2가지
        - 타임아웃(5초 초과) → 캐시된 응답 반환 또는 안내 메시지
        - Rate Limit(429) → Circuit Breaker 오픈, 기본 응답 반환
    - 환각 방어 1가지 이상 (존재하지 않는 게시글 정보 생성 시 차단)
    - 비용 로깅 항목: `requestId`, `promptTokens`, `completionTokens`, `latencyMs`, `model`, `status`, `errorType`
    - 토큰 사용량·응답 지연·에러율 대시보드 구성

- **시나리오 예시**
    
    ```
    [1턴] "오늘 점심 같이 먹을 사람 찾아줘"      → "몇 시가 편하세요?"[2턴] "1시 반"      → "정문이랑 후문 중 어디가 가까우세요?"[3턴] "정문"      → "1시 반 정문 게시글 찾았어요. 책임비 500P짜리인데 신청할까요?"
    ```
    
- **내용**

## 5. MVP 정책

### 1. 가입

- 학교 이메일(.ac.kr)
- 한 이메일당 한 계정

### 2. 게시글

- 최소 예치 포인트 200P
- 책임비 포인트 100P 단위 증감 설정 (본인 보유 한도 내)
- 최소 인원 2명 / 최대 인원 10명 (등록자 포함)

### 3. 매칭

- 1:1 / 1:N 선착순 매칭
- 신청 시(＝매칭 시) 등록자 예치 포인트와 동일한 포인트 차감
- 만남 완료 후 예치 포인트 환수
- 매칭 후 만남 희망 시간 이전까지 10분 1회 연장 가능

### 4. 포인트

- 가입 시 10,000P
- 게시글 작성·신청 시 예치(최소 200P)
- 예치 포인트는 100P단위로 증감
- 매칭 취소 포인트 정책
    - 1:1 매칭 취소
        - 취소한 사람의 예치 포인트 50% 몰수
        - 상대방 예치 포인트 100% 반환
        - 누가 취소하든 동일하게 적용
        - 등록자가 취소할 경우 POST는 CANCELLED로 전환
    - 1:N 매칭 취소
        - 신청자가 취소하는 경우
            - 취소한 신청자의 예치 포인트 50% 몰수
            - 해당 신청자만 모임에서 퇴장
            - 나머지 신청자와 모임은 유지
            - POST 상태 OPEN 유지
        - 등록자가 취소하는 경우
            - 귀책이 등록자에게 있으므로 모든 신청자 예치 포인트 100% 반환
            - 등록자 예치 포인트 50% 몰수
            - POST 상태 CANCELLED로 전환
- 매칭 취소 시 예치 포인트 50% 반환
- 노쇼 시 예치 포인트 전체 차감
- 잔액 부족 시 게시글 작성·신청 불가 → 포인트 충전으로 연계

### 5. 식대

- N빵 기본 원칙
- 회원가입 약관 동의로 명시

### 6. 안전 (약관 명시)

- 시스템 강제 정산 X (오프라인 협의)
- 만남 장소는 공공장소 권장(밀폐된 공간x)
- 회원가입 시 약관 동의 진행

### 7. 노쇼 정책

> 
> 
> 
> **도덕적 판단이 아닌 시스템 규칙 기반 자동 판정**
> 
> 분쟁이 발생하지 않도록 **규칙 자체가 곧 판정 기준**이 된다. 사용자는 규칙을 알고 따르기만 하면 안전하다. 규칙을 어긴 쪽이 노쇼로 처리된다.
> 

```java
0. 해피 패스
		약속시간 10분 전 ~ 30분 후까지 GPS 기반 장소 인증 가능
		장소 인증 완료 시 만남 QR 발급 -> 등록자(QR 표시), 신청자(스캔) 인증
		-> 예치포인트 반환

1. 약속시간 이전에 사전 취소하는 경우 -> 취소자 예치 포인트 50% 몰수, 상대방(또는 단체매칭의 나머지 참여자)은 100% 반환
2. 약속시간 이전에 채팅으로 늦음 공지 -> 약속시간 이전에만 10분 1회 연장 가능 (상대방 동의 필요, 수락 대기 타임아웃 5분)
3. 사전 공지 없이 진행되는 경우 -> 노쇼 예정으로 분류된 사용자 예치포인트 반환 없음 (확정 시)
	3-1. 장소 인증 활성화 시간(약속시간 -10분 ~ +30분) 만료 시점에 반경 안에 없는 쪽이 노쇼 예정(HOST_NO_SHOW / GUEST_NO_SHOW)
	3-2. 둘 다 반경 밖이면 BOTH_NO_SHOW
	3-3. 장소 인증 완료 후 QR 미인증 상태로 QR 만료(장소인증완료 + 30분)되면, 만료 직전 반경 안에 없는 쪽이 노쇼 예정
	3-4. QR 만료 시점에 둘 다 반경 안에 있으면 노쇼가 아니라 매칭 취소 처리

억울한 노쇼 방지
- 노쇼 예정 상태임을 먼저 안내.
  24시간 안에 이의제기가 없을 경우 노쇼로 최종 판정한다. (장소 인증 완료자만 이의제기 가능)
	  ex. "'닉네임'님은 현재 'match_id'만남에서 노쇼 예정 상태입니다. 동의하십니까?
	  해당 사안에 대해 24h안에 응답이 없을 경우 예치 포인트가 차감됨을 알려드립니다"
```

### GPS 장소 인증 + QR 만남 인증 기반 판정 (실제 구현)

- `meet_verification` 테이블의 `author_place_verified_at`, `applicant_place_verified_at`로 장소 인증 노쇼를 판정하고, QR 스캔 완료 여부로 만남 인증 노쇼를 판정한다.
- 상태값은 `VerificationStatus` enum 기준: `HOST_NO_SHOW`(등록자 노쇼), `GUEST_NO_SHOW`(신청자 노쇼), `BOTH_NO_SHOW`(양측 노쇼) — 기존 `AUTHOR_NO_SHOW`/`APPLICANT_NO_SHOW` 명칭에서 단체매칭 대응을 위해 `HOST`/`GUEST`로 변경됨

| 등록자 GPS 진입 | 신청자 GPS 진입 | 판정 |
| --- | --- | --- |
| O | O | 장소 인증 완료 → QR 단계 진입 |
| X | O | `HOST_NO_SHOW` |
| O | X | `GUEST_NO_SHOW` |
| X | X | `BOTH_NO_SHOW` |
- GPS 장소 인증 활성화 시간: 약속 시간 10분 전 ~ 30분 후, GPS 반경 50m
- 장소 인증 완료 시 만남 QR 토큰 발급, 유효 기간(`expires_at`)은 **장소 인증 완료 시점 + 30분**이며, 경과 시 `EXPIRED` 처리
- QR 단계에서도 동일하게 만료 직전 반경 안에 없는 쪽을 `HOST_NO_SHOW`/`GUEST_NO_SHOW`/`BOTH_NO_SHOW`로 판정하며, 둘 다 반경 안에 있으면 매칭 취소 처리

### 억울한 노쇼 방지 (이의 제기 절차)

- 노쇼 예정으로 먼저 분류 (`_NO_SHOW` 상태)
- **24시간 이내 이의 제기가 없으면** 노쇼 확정 및 예치금 환수
- 이의 제기 시 작성한 사유를 바탕으로 관리자 검토 후 최종 판정 (채팅 기록 등 보존된 자료 활용)
- 노쇼 당한 사람끼리 같은 반경안에 있으면 매칭 추천해주는 기능 도입 예정

## 9. 주요 설계 포인트

**선착순 매칭 동시성**

- 신청 요청에 대해 `match` row 생성 시 `post_id`에 UNIQUE 제약으로 1차 방어
- Redis 분산락(`lock:post:{postId}`)으로 동시 요청 직렬화
- 트랜잭션 내에서 게시글 상태 변경 + 매칭 생성 + 포인트 차감 + 채팅방 생성을 원자적으로 처리

**실시간 채팅**

- WebSocket / STOMP 기반 클라이언트 실시간 통신
- Kafka Producer/Consumer 기반 멀티 인스턴스 메시지 분배
- 채팅 메시지는 `chat_message` 테이블에 영구 저장

**스케줄러**

- Redis Key TTL + Keyspace Notification 또는 Spring `@Scheduled` 활용

**포인트 정합성**

- 모든 포인트 변동은 트랜잭션 내에서 `point_transaction` 기록과 함께 발생
- 분쟁 시 `point_transaction` 누계로 `user.point` 검증

<details>
<summary><strong>10. 고도화 정책</strong></summary>

## 10. 고도화 정책

#### 알림 정책

- 알림 보존 기간은 10일로 지정
- 10일이 지나면 스케줄러가 자동 삭제
- 알림은 한 번에 최대 50개 조회 (커서 기반 스크롤)
- 종 모양 클릭으로 목록 조회, 전체 읽음 버튼 클릭으로 읽음 처리
- 알림은 비동기(@Async) 처리 → 알림 발송 실패 시에도 핵심 로직은 정상 동작
- 정상 종료 / 타임아웃 / 에러 발생 시에도 다른 로직은 정상 처리
- SSE 타임아웃: 30분
    - 타임아웃 시 이미터 연결을 종료해야 동일 알림 중복 전송 방지
    - 흐름: 이미터 저장소 등록 → SSE 연결 → 30분 타이머 → 이벤트 전송 → 타임아웃 시 연결 종료
- SSE 연결이 없는 유저에게는 DB 저장만 하고 실시간 전송 스킵
- **노쇼 알림 정책**
    - 노쇼 관련 알림(NO_SHOW_WARNING, NO_SHOW_CONFIRMED)은 MeetVerification 단위로 중복 발송 방지 처리됨
    - NO_SHOW_WARNING 발송 시점에 채팅방이 READ_ONLY로 전환됨
    (이의 신청 기간 중 채팅 내역 열람 가능, 신규 메시지 전송 불가)
    - NO_SHOW_CONFIRMED 시점에는 채팅방 상태 변경 없음
- **만남 리마인드 알림 정책**
    - 만남 임박 / 30분 전 / 15분 전 알림은 만남 1건당 각 1회씩만 발송
    - 그룹 만남의 경우 참여자 수와 관계없이 만남 단위로 중복 없이 발송

#### 그룹채팅

- **기본 원칙**
    - 등록자(HOST)는 모임 전체에 대한 책임을 가진다.
    - 신청자(GUEST)는 자신의 개별 매칭에 대해서만 책임을 가진다.
    - 노쇼 제재는 해당 사용자의 책임 범위까지만 적용한다.
    - 채팅방은 postId 기준으로 하나 생성된다.
    - 신청자별 참여 및 제한 상태는 ChatMember에서 관리한다.
- **채팅방 생성**
    - 첫 신청자가 신청하면 채팅방을 즉시 생성한다.
    - 게시글 등록자는 HOST로 참여한다.
    - 신청자는 GUEST로 참여한다.
    - 이후 신청자는 기존 채팅방에 GUEST로 추가한다.
    - 1:1 및 그룹 채팅 모두 지원한다.
- **채팅 권한**
    - **정상 참여자**
        - 채팅방 메시지 전송 가능
        - 본인의 입장 시점 이후 메시지 조회 가능
        - 채팅 메시지 실시간 수신 및 알림 수신 가능
    - **참여자가 아닌 사용자**
        - 메시지 전송 및 조회 불가
        - CHAT_NOT_PARTICIPANT 오류 반환
- **노쇼 처리**
    
    
    | **노쇼 유형** | **채팅 처리** |
    | --- | --- |
    | GUEST_NO_SHOW | 해당 신청자만 NO_SHOW 처리 |
    | HOST_NO_SHOW | 채팅방 전체를 즉시 READ_ONLY로 전환 |
    | BOTH_NO_SHOW | HOST 노쇼가 포함되므로 전체 READ_ONLY 전환 |
    - **GUEST 노쇼**
        - 채팅방 전체 상태는 ACTIVE로 유지한다.
        - 해당 GUEST의 ChatMember.status를 NO_SHOW로 변경한다.
        - 노쇼 판정 시각을 leftAt에 저장한다.
        - 메시지 전송을 즉시 차단한다.
        - 채팅 메시지 실시간 수신 및 수신 알림을 차단한다.
        - 노쇼 판정 이전 메시지만 조회할 수 있다.
        - 다른 정상 참여자는 계속 채팅할 수 있다.
        
        `joinedAt <= message.createdAt < leftAt`
        
    - **HOST 또는 양측 노쇼**
        - 채팅방 전체를 즉시 READ_ONLY로 변경한다.
        - 모든 참여자의 신규 메시지 전송을 차단한다.
        - 기존 메시지는 조회할 수 있다.
        - 채팅방은 다시 ACTIVE로 복구하지 않는다.
- **만남 완료**
    - QR 인증으로 만남이 완료되면 채팅방은 즉시 종료되지 않는다.
    - 완료 시점부터 2시간 후 전체 READ_ONLY로 전환한다.
    - READ_ONLY에서는 메시지 조회만 가능하다.
- **매칭 취소**
    - **GUEST 취소**
        - 해당 GUEST를 ChatMember에서 제거한다.
        - 제거된 사용자는 채팅방에 접근할 수 없다.
        - 나머지 참여자의 채팅방은 유지한다.
        - 게시글은 정원에 따라 다시 신청 가능한 상태가 된다.
- **HOST 또는 1:1 매칭 취소**
    - 채팅방 전체를 DEACTIVATED로 변경한다.
    - 메시지 전송과 조회를 모두 차단한다.
- 메시지 조회
    - 커서 기반 페이징 (최신순)
    - 한 번에 최대 20개
    - 읽기 전용 : 비활성화 후에도 조회 가능
    - 완전 비활성화 : 조회 불가

#### 후기 정책

- 후기 작성 조건
    - 후기는 매칭 상태가 COMPLETED인 경우에 작성할 수 있다.
    
    작성 가능 대상은 다음과 같다.
    
    - 1:1 만남
        - 신청자만 만남에 대한 후기를 작성할 수 있다.
    - 1:N 만남
        - 신청자들이 만남 자체에 대한 후기를 작성한다.
        - 작성된 후기의 평균값으로 만남을 주선한 등록자의 매너온도에 반영된다.
        - 신청자들끼리는 서로 후기를 작성하지 않는다.
        
        후기 작성 가능 기간은 만남 완료 시점부터 7일 이내로 제한한다.
        
- 후기 수정 / 삭제 정책
    - 후기는 한 번 작성하면 수정 및 삭제할 수 없다.
    - 후기는 만남 이후의 경험을 기록하는 데이터이므로, 작성 시점의 평가를 그대로 보존한다.
- 후기 태크 정책
    - 후기 작성 시 사용자는 다음 중 하나의 후기만 보낼 수 있다.
    - 좋았어요
    - 아쉬웠어요
    
    각 방향에는 최대 5개의 태그가 존재한다.
    
    좋았어요 태그 예시:
    
    - 시간 약속을 잘지켰어요.
    - 대화 코드가 잘 맞았어요.
    - 부담 없이 편하게 밥 먹는 분위기였어요
    - 식사 매너가 좋았
    - 다음에 또 한 끼 같이하고 싶어요
    
    아쉬웠어요 태그 예시:
    
    - 약속 시간에 늦었어요
    - 소통이 잘 안 되고 조금 어수선했어요
    - 생각했던 만남(모임)과 성격이 달랐어요
    - 식사 매너가 아쉬웠어요
    - 다시 만나고 싶지 않아요
    
    단, 좋았어요 태그와 아쉬웠어요 태그는 동시에 선택할 수 없다.
    
- 신고 연계 정책
    - 아쉬웠어요 태그 중 ’다시 만나고 싶지 않아요’를 선택하면 상호 블라인드 처리된다.
- 매너온도 반영 정책
    
    매너온도는 작성된 후기들의 점수를 기반으로 **만남(모임) 단위의 평균 변화량**을 계산하여 누적 반영한다.
    
    범위는 다음과 같다.
    
    - 최저: 0도 / 최고: 99도 / 기본값: 36.5도
    - 계산식: `매너온도 = 현재 매너온도 + (새로운 모임 평균 점수 - 이전 모임 평균 점수) × 0.5(가중치)`
        - *소수점 첫째 자리로 반올림하여 표기한다.*
- **매너 점수 산정 방식 (역산 방지 및 어뷰징 제한)**
    - 후기 태그 선택 개수를 기본 점수로 환산하되, 상대방이 몇 개의 태그를 골랐는지 유추할 수 없도록 한 만남당 최대/최소 제한(Clamp)을 적용한다.
        
        ```jsx
        [좋았어요 (Positive)]
        태그 1개 선택 → +1점
        태그 2개 선택 → +2점
        태그 3개 이상 선택 → +2점 (최대 상한선 보정)
        
        [아쉬웠어요 (Negative)]
        태그 1개 선택 → -1점
        태그 2개 선택 → -2점
        태그 3개 선택 → -3점
        태그 4개 이상 선택 → -3점 (최소 하한선 보정)
        ```
        
    - **좋았어요**는 선택 개수가 많을수록 높은 점수로 반영하되 최대 +2점을 넘지 못한다.
    - **아쉬웠어요**는 선택 개수가 많을수록 낮은 점수(마이너스)로 반영하되 최소 -3점보다 낮아지지 않는다.
    - 결과적으로 한 명의 신청자가 줄 수 있는 점수는 **3점 ~ +2점 사이로 제한**되어 완벽한 익명성을 보장한다.
- **1:N 만남의 매너온도 반영**
    - 단체 만남(1:N)에서도 후기는 개별 신청자가 독립적으로 작성하며, 평가 대상은 만남을 주선한 등록자(호스트)다.
    - 단체 만남에서 여러 명이 동시에 평가할 경우, 개별 점수의 합산이 아닌 해당 만남의 '평균 점수'를 기준으로 등록자의 매너온도에 반영한다.
        
        ```jsx
        등록자 A의 모임 (기존 평균 점수: 0점)
        - 신청자 B 후기 점수: +2점 (태그 2개 이상 선택)
        - 신청자 C 후기 점수: +2점 (태그 2개 이상 선택)
        - 신청자 D 후기 점수: -3점 (태그 3개 이상 선택)
        
        ▶ 해당 만남의 최종 평균 점수 = (+2 + 2 - 3) ÷ 3 = +0.33점
        ▶ 등록자 A의 매너온도 반영식 = 기존 온도 + (+0.33 - 0) × 0.5 = +0.165도 (반올림하여 +0.2도 변동)
        ```
        
        즉, 단체 만남에서 다수의 신청자가 참여하더라도 '모임 평균값'으로 치환되어 점수가 계산되므로, 신청자 수가 많다고 해서 등록자의 매너온도가 과도하게 급등하거나 급락(테러)하는 것을 방지한다.
        
- 탈퇴 유저의 후기
    - 탈퇴한 유저의 후기도 1:N 만남에서는 신청자들이 작성한 후기와 함께 등록자의 매너온도를 반영되어있다.
- 후기 조회 정책
    - 사용자는 내가 작성한 후기만 조회할 수 있다.
    - 사용자는 내 매칭 조회 화면에서 ‘내가 작성한 후기 보기’ 버튼을 통해 후기를 조회할 수 있다.
- 후기 작성 알림 정책
    - 후기 작성 알림은 다음 시점에 발송한다.
        - 만남 인증 완료 후 2시간이 경과하여 채팅방이 읽기 전용으로 전환될 때
        → "만남이 완료되었습니다. 후기를 작성해주세요!"
        (스케줄러가 만남 완료 시점 기준 +2시간 후 채팅방 비활성화 처리 시 함께 발송)
        - 후기 작성 가능 기간 마지막 날 → “오늘이 후기를 작성할 수 있는 마지막 날입니다. 서둘러 작성해주세요!”
    - 후기 작성 가능 기간은 만남 완료 시점부터 7일이며, 7일이 지나면 후기 작성 버튼은 비활성화된다.

- DB에서 관리할 때는 무료 먼저 차감 후 유료 차감

#### 노쇼 이의제기 정책

- **스케줄러 지연 예외 처리**
    
    장소 인증 또는 QR 인증 처리 과정에서 서버 스케줄러 지연이 발생한 경우,
    노쇼 예정 알림이 실제 만료 시각보다 늦게 발송될 수 있다.
    이 경우 author_place_verified_at, applicant_place_verified_at,
    QR expires_at 등 DB에 기록된 실제 인증 시각을 기준으로 상황을 추적할 수 있으므로,
    스케줄러 지연으로 인한 노쇼 판정 이의는 고객센터 1:1 문의를 통해 처리한다.
    
- 노쇼 예정 상태 알림이 발송된 시점을 기준으로 24시간 이내에 이의제기 가능
(장소 인증 만료, QR 만료 등 노쇼 예정 판정 경로가 다양하므로,
기준 시각은 시스템이 노쇼 예정 상태를 판정하고 알림을 발송한 시각으로 통일)
- 장소 인증 완료자 → 이의 제기 가능 (가능한 사유 6개 드롭다운 선택) → 각 필요한 증빙 자료 업로드 및 사유 작성
    - **장례식 증빙 자료 → 매칭 취소 처리**
    - **응급실(확인서) → 매칭 취소 처리**
    - **스마트폰 고장 → 만남인증 완료한 증빙**
    - **GPS 인증 오류 → 만남인증 완료한 증빙**
    - **QR 코드 인식 오류 → 만남인증 완료한 증빙**
    - **관리자 권한으로 허용**

| --- | --- | --- |
| **장례식** | - 모바일 부고장 캡처 화면 (시간과 날짜)
- 사망진단서 외 | 갑작스러운 가계의 대소사를 증빙할 수 있는 텍스트/이미지 |
| **응급실 내원** | - 응급실 진료비 영수증
- 처방전 또는 응급실 내원 확인서
- 약 처방 영수증 (날짜, 시간) | 비용이나 병원명, 날짜가 선명하게 찍힌 영수증이 가장 간편합니다. |
| **스마트폰 고장** | - 서비스센터 수리 접수증/영수증 사진
- 대여폰/공기계 이용 화면 인증 | 고장 난 당일 혹은 이튿날 서비스센터를 방문했다는 증명서가 확실합니다. |
| **GPS 인증 오류** | - 해당 장소에서 찍은 **날짜/시간/위치 정보가 포함된 원본 사진**
- 타사 지도 앱(네이버/구글)의 현재 위치 캡처 화면 | 기본 카메라로 찍은 사진은 상세 정보에 촬영 시간과 위치가 남으므로 좋은 증거가 됩니다. |
| **QR 코드 인식 오류** | - QR 스캔 화면에서 오류 팝업이 뜬 캡처 화면
- 상대방 화면의 QR을 내 폰으로 찍은 사진 | 인식이 안 되는 먹통 상태를 보여주는 화면 캡처나 에러 메시지 캡처 |
| **기타 (관리자 판단)** | - 자유 형식의 설명 및 관련 참고 사진 | 위 5개 외에 특수한 상황을 대비한 자유 업로드 |
- 관리자가 접수 후 영업일 기준 2~3일 이내 처리(예정)
- `SUBMITTED`  → `UNDER_REVIEW` 전환은 관리자가 상세조회 하는 순간 자동으로 전환
- `HOLD` (보류) 상태일 때만 다시 이의제기 신청 가능, (같은 카테고리에 대해서만)
- `HOLD` 상태에서 24시간 이내 이의제기를 재신청 해야하고, 24시간이 초과 → 이의제기 재요청 불가
    - 관리자가 `HOLD` 판정을 내려준 시점부터 24시간 카운팅 시작

**판정 결과별 포인트 처리**

| 판정 | 이의제기자 |
| --- | --- |
| `ACCEPTED` (수용) | 예치금 100% 반환 |
| **`PARTIALLY_ACCEPTED`** (부분 수용) | 예치금 50%만 반환 |
| `REJECTED` (반려) | 그대로 몰수 |
| `HOLD`  | 보류 |
| `SUBMITTE`  | 제출 완료, 검토 대기 |

#### 신고 정책

- 동일 게시물 재신고 제한 (악의성 방지) - 기각(`REJECTED`) 된 게시물 신고에 대해 3일 이내 재 신고 불가 단, **수정된 게시글**에 한해서는 재 신고 가능
- 신고 포상 50P 지급 조건 - 채택(`ACCEPTED`) 시에만 지급, 동일 유저의 월별 포상은 최대 300P까지만 (어뷰징 방지)
- 관리자 판단하에 삭제 할 수도 있음 - 관리자 권한
- 관리자가 게시물을 삭제 하려고 할 때 해당 게시물에 대한 신고 건이 있다면 알림을 띄우고 신고 채택 및 게시글 삭제 버튼으로 자동으로 채택, 포상금 지급과 게시물 삭제가 이루어지도록 구현
    - 관리자와 게시물 신고가 동시에 이루어질 경우를 대비해 동시성 제어를 추가
- 게시글이 신고 상태라서 매칭을 신청 할 수 없습니다.
- 게시글 강제 삭제 → 등록자 예치 포인트 전액 환불 (신고 당한 게시물 + 관리자 판단하에 삭제 (`reportId` = null))
- 신고자 제재 (신고를 한 사람)
    - 신고자의 누적 기각 횟수가 3의 배수(3회, 6회, 9회...)가 되는 즉시 10일간 신고 기능이 박탈된다.
        - 기각 횟수는 신고 접수 횟수가 아니라 `REJECTED` 처리된 신고 건수만 누적한다.
        - 채택된 신고는 기각 횟수에 포함하지 않으며, 누적 기각 횟수를 초기화하지도 않는다.
        - 박탈 기간이 종료되면 신고 기능은 복구되지만 누적 기각 횟수는 유지된다.

```jsx
        1번째 신고 → 기각 → rejectedCount = 1 → 신고 가능
        2번째 신고 → 기각 → rejectedCount = 2 → 신고 가능
        3번째 신고 → 기각 → rejectedCount = 3 → 10일간 신고 기능 박탈

        박탈 기간 종료 후 신고 기능 복구

        4번째 신고 → 채택 → rejectedCount = 3 → 기각 횟수 변동 없음
        5번째 신고 → 기각 → rejectedCount = 4 → 신고 가능
        6번째 신고 → 기각 → rejectedCount = 5 → 신고 가능
        7번째 신고 → 기각 → rejectedCount = 6 → 다시 10일간 신고 기능 박탈
```

- 피신고자 제재 (신고를 당한 사람)
    - 작성한 게시글이 신고를 당함으로 **삭제 처리**된 건의 누적 횟수에 따른 제재 정책
        - 작성한 게시글에 대한 신고가 **채택되고, 해당 게시글이 삭제 처리된 누적 횟수**에 따라 제재한다.
            
            
            | 채택 누적 횟수 | 제재 | 알림 메시지 |
            | --- | --- | --- |
            | 1회 | 경고 | "신고가 채택되었습니다. 서비스 이용 규정을 준수해 주세요." |
            | 2회 | 경고 | "두 번째 경고입니다. 재발 시 계정이 정지될 수 있습니다." |
            | 3회 | 3일 정지 | "세 번째 규정 위반으로 계정이 3일간 정지되었습니다." |
            | 4회 | 10일 정지 | "네 번째 규정 위반으로 계정이 10일간 정지되었습니다." |
            | 5회 | 30일 정지 | "다섯 번째 규정 위반으로 계정이 30일간 정지되었습니다." |
            | 6회 이상 | 영구 정지 | "지속적인 규정 위반으로 계정이 영구 정지되었습니다." |

#### 만남 시간 연장 정책

- 연장 요청은 만남 시간 5분 전까지 가능 (ex. 약속시간 11시 → 10시 55분까지 연장 요청 가능)
    - 매칭이 된 시점부터 약속시간 5분 전까지(요청에 제한은 없음)
- 상호 동의 하에 연장 가능
- 요청 → 상대방 수락/거절 → 처리
- 수락 대기 타임아웃(5분) → 만료 (재요청 가능)
- 만남 시간 연장은 1회 한정 → 10분 연장
- 만료 후 재요청 -> 가능 (단, 수락/거절 상태에선 영영 불가)
- 누가 수락 권한? -> 요청자가 아닌 매칭 당사자(상대방)만
누가 거절 권한? -> 동일 (요청자는 자기 요청 취소 불가, 그냥 만료 기다림)
- 연장 요청을 보낼 수 있는 횟수 제한은 없으나, 한번 보냈을때 5분동안 대기해야됨,
상대방이 수락 -> 바로 끝
또 보낼라고 해도 5분 기다렸다가 보내야 됨
